**Cordon 0.7.1**

Cordon is a Crystal shard that runs shell commands inside a platform-native sandbox with a configurable access policy. It works on macOS (via `sandbox-exec` / Seatbelt), Linux (via `bwrap` / Bubblewrap) and, as a preview, Windows 11 (via Microsoft's MXC `wxc-exec.exe`), presenting all three as a single clean API.

**Changes**

* **Windows: MXC 1.0.0** - Cordon now uses `@microsoft/mxc-sdk` 1.0.0, MXC's first stable release, and emits its `1.0.0` config contract. MXC 1.0.0 rejects the configs Cordon 0.7.0 produced, and Cordon 0.7.1 looks for `wxc-exec.exe` 1.0.0 only, so the two must be upgraded together.
  - **Action required:** rerun `scripts/check-windows.ps1 -Install` (add `-AllUsers` if you installed for all users). It installs 1.0.0 beside the old version. Add `-Prune` to delete older versions once the check passes; leave it off if another app on the machine still uses Cordon 0.7.0.
  - Enforcement is unchanged: network access is still allowed or blocked as a whole, and inbound and host-loopback traffic stay blocked.
* **`check-windows.ps1 -Prune`** - After a successful check, deletes MXC versions older than the one this Cordon uses from the per-user folder, or with `-AllUsers` the all-users folder. Newer versions and unrecognised folders are kept, and nothing is deleted unless the current version is installed there.
* **Tested with Crystal 1.21** - CI now builds and runs the specs with Crystal 1.21 on Windows and on some of the macOS and Linux runners.

**Known issues**

* `Policy#env` and `Policy#unset_env` are honoured on Linux and Windows but silently ignored by the macOS runner, which inherits the parent environment instead. See [#24](https://github.com/ModelArmy/cordon.cr/issues/24).
* Windows: MXC 1.0.0 no longer carries the "early preview, not a security boundary" warning of earlier releases, but PSEC is new and may change between Windows updates. Cordon pins the MXC version it is tested against; re-run `cordon confirm` after Windows updates ([#41](https://github.com/ModelArmy/cordon.cr/issues/41)).
* Windows: a batch file (`.bat`, `.cmd`) can only be run with `shell: true`, because its arguments cannot be quoted safely.
* Windows: tested on Windows 11 Enterprise 25H2, on ARM (a VM and GitHub's Windows 11 ARM runner, with `cordon.exe` under x64 emulation) and on an x64 laptop. Other editions such as Windows 11 Pro are not yet tested.
* Windows: whether a machine has the process security environment does not follow from its build number alone. A fully updated laptop that reported it unavailable had it a week later; if `check-windows.ps1` reports it unavailable, install pending updates and check again in a few days.
* Windows: only an x64 `cordon.exe` is built; ARM machines run it under emulation ([#39](https://github.com/ModelArmy/cordon.cr/issues/39)).
* Windows: `cordon.exe` is unsigned, and some endpoint security products flag the statically linked executable as suspicious ([#40](https://github.com/ModelArmy/cordon.cr/issues/40)).
* Windows: everything under `C:\Windows` is readable and executable in the sandbox without a grant ([#38](https://github.com/ModelArmy/cordon.cr/issues/38)).
* Windows: PowerShell 7, Git Bash, toolchains installed per user, and junctions or symlinks inside granted paths are not yet validated ([#34](https://github.com/ModelArmy/cordon.cr/issues/34), [#35](https://github.com/ModelArmy/cordon.cr/issues/35), [#36](https://github.com/ModelArmy/cordon.cr/issues/36)).
